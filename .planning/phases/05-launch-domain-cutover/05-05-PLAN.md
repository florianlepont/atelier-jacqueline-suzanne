## Phase Goal

> **Source note:** `.planning/ROADMAP.md` Phase 5 carries `**Mode:** mvp` but its `**Goal:**` line is not in `As a … I want to … so that …` form. This planner does not invent a user story. ROADMAP goal, verbatim: *"The new site fully replaces the old Myportfolio site at the live domain, with no unplanned downtime or broken email."* Run `/gsd mvp-phase 5` if a formal user-story goal line is wanted.

**This is the irreversible plan.** Everything before it was reversible by `git revert`. This plan writes files to a server the maintainer owns and repoints a live domain that carries active email. Both actions are gated on explicit human approval per D-02 and D-04.

<objective>
Execute the cutover: capture the authoritative DNS zone, obtain explicit human go-ahead, push the built site to OVH, and then repoint the domain's address records at it.

Purpose: this is the single step that satisfies ROADMAP success criterion 1. It is deliberately ordered upload-first, DNS-second — files sitting in the OVH webroot are unreachable until DNS points there, so the actual switch is instantaneous and there is never a moment where the domain resolves to an empty server.
Output: `05-DNS-BASELINE.md` (the pre-change zone, the rollback source of truth), `05-mx-baseline.txt` (machine-readable input for the post-cutover MX diff), a completed production SFTP push, and the modified A records.

**Note on task count:** this plan has four tasks rather than the usual two-to-three. Two of them are human gates with negligible context cost, and the remaining two are a `gh` dispatch and a control-panel edit. They are kept in one plan on purpose: putting a plan boundary between the SFTP push and the DNS flip would break the runbook's requirement that they happen sequentially in one supervised session.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator → OVH DNS zone | The single edit surface where a mistake removes the domain's mail routing. No automated guard exists; only the runbook, the captured baseline, and the scoped-edit discipline. |
| GitHub Actions → OVH webroot | A credentialed write to the maintainer's hosting account, executed by third-party Docker code. |
| the live domain → the public | Between the DNS flip and verification, whatever is in the webroot is what the world sees. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-03 | Tampering / Denial of Service | OVH DNS zone — MX loss during the cutover | critical | mitigate | Task 1 captures both a resolver view and (at Task 2) OVH's own full zone export before any edit (D-04). Task 4 restricts the change to two `A` records via per-record Modify, and names zone reset, zone recreation, MX/SPF/NS edits, and bulk text paste as prohibited. Task 4's verification diffs MX before looking at the website at all, and any difference is an immediate no-deliberation rollback with the values already written down in `05-DNS-BASELINE.md`. |
| T-05-20 | Denial of Service | pointing DNS at an empty webroot | high | mitigate | Ordering: the SFTP push (Task 3) completes and is verified successful BEFORE the DNS edit (Task 4), and Task 3 explicitly halts the plan if the deploy job fails.
