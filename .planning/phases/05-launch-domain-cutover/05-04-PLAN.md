  <action>
Create `scripts/launch-smoke-check.sh`, executable (`chmod +x`), with a `#!/usr/bin/env bash` shebang and `set -uo pipefail` (deliberately NOT `-e`: the script must run every probe and report all failures, mirroring the `failures` accumulator pattern already used in `tests/scripts/verify-static-artifact.mjs`).

Interface:
- First positional argument: the origin to probe, e.g. `https://atelierjacquelinesuzanne.fr`. Default to that same production origin when omitted.
- `BASE` env var, default `/` — the path prefix, so the same script works against the GitHub Pages project-page build at `/ajs-website/`.
- `SKIP_PHP` env var, default `0` — set to `1` when probing an origin with no PHP runtime (GitHub Pages).
- `MX_BASELINE` env var, optional path to a file holding the expected `dig +short MX` output; the MX comparison is skipped when unset.

Implement a `check <label> <condition-command>` style helper that appends to a `failures` array and prints a `PASS`/`FAIL` line per probe, then exits `1` if the array is non-empty and `0` otherwise, printing a final count.

Probes, in this order:

1. **Reachability.** For each of `${BASE}`, `${BASE}en/`, `${BASE}about/`, `${BASE}contact/`, `${BASE}editions/`, `${BASE}sitemap.xml`, `${BASE}robots.txt`: `curl -sS -o /dev/null -w '%{http_code}' --max-time 20 -L "<origin><path>"` must be `200`. Use `-L` so an http→https or trailing-slash redirect does not read as a failure.
2. **Custom 404.** Request a path that cannot exist (e.g. `${BASE}__smoke_check_missing__/`) and require HTTP `404`. Also require the response body to contain the site's own 404 marker rather than the host's default error page — assert the body contains `404`, and, since Astro's prerendered `404.astro` always contains links back to both locale roots, assert the body contains `href="${BASE}en/"`. This is the single check that proves `ErrorDocument 404 /404.html` from `public/.htaccess` actually took effect on Apache.
3. **Identity.** The homepage body must contain `Atelier Jacqueline Suzanne`. This is what distinguishes "the new site is live" from "the old site is still live" for ROADMAP success criterion 1.
4. **Canonical origin.** Fetch `${BASE}sitemap.xml` and require the body to contain the origin string it was fetched from. This catches RESEARCH.md Pitfall 4 — a production build that forgot `SITE_URL` and therefore advertises `florianlepont.github.io` in its sitemap, canonical tags, and hreflang links. Also fetch `${BASE}robots.txt` and require it to reference `${BASE}sitemap.xml`.
5. **PHP endpoint** (skipped entirely when `SKIP_PHP=1`):
   a. `curl -sS -o /dev/null -w '%{http_code}' -X GET "<origin>${BASE}contact.php"` must be `405` — proves PHP is executing rather than the file being served as source, and proves the method guard works.
   b. `curl -sS --max-time 20 -X POST -F 'name=Smoke Check' -F 'email=smoke@example.com' -F 'message=automated smoke check' -F 'website=smoke-check-honeypot' "<origin>${BASE}contact.php"` must return HTTP 200 with a body containing `"success":true`. The non-empty `website` field makes this a honeypot-triggered submission, so the endpoint short-circuits and **sends no mail** — this probe is safe to run repeatedly and never touches the real mailbox. Put that fact in a comment directly above the probe, because it is the reason the script is safe to run in a loop during troubleshooting.
   c. A malformed submission — same fields but `email=not-an-email` and an empty `website` — must return HTTP `400`. This proves server-side validation is active and not merely present in source.
6. **MX preservation** (skipped when `MX_BASELINE` is unset): run `dig +short MX <host-derived-from-origin>` , sort it, and `diff` against the sorted contents of `$MX_BASELINE`. Any difference is a failure with a loud message naming email breakage, since this is the check standing between the cutover and ROADMAP success criterion 2. Derive the hostname from the origin by stripping the scheme and any path.

Add a header comment block stating what the script is for, the three ROADMAP success criteria it maps to, and two usage examples: the staging rehearsal and the production run.

Then add to `package.json` `scripts`: `"test:smoke": "bash scripts/launch-smoke-check.sh"`, placed after `test:artifact` to match the existing ordering. Do not add it to any CI workflow — it probes live external hosts, which does not belong in a build gate.

**Rehearse it.** Run it against the live staging site with the PHP probes disabled, since GitHub Pages has no PHP runtime and (per plan `05-01`) no longer publishes `contact.php` at all:

`BASE=/ajs-website/ SKIP_PHP=1 npm run test:smoke -- https://florianlepont.github.io`

It must exit 0. If any reachability or canonical probe fails against staging, the probe is wrong (staging is known-good) — fix the script, not the site. Record the rehearsal output in the SUMMARY: that transcript is the concrete evidence for ROADMAP success criterion 3's "rehearsed" clause.

Then, in bold, the prohibitions: do NOT use the zone's "Reset the DNS zone" function (OVH documents it as reverting to a minimal default configuration, which deletes the MX records and breaks Romane's email); do NOT delete and recreate the zone; do NOT touch the MX, SPF TXT, or NS records; do NOT bulk-paste a replacement zone in text mode, because that makes an MX omission a single silent keystroke.

**Section 4 — Verify.** In order:
- `dig +short MX atelierjacquelinesuzanne.fr` and diff against the section 1 capture. This runs first, before anything about the website is checked, because email is the higher-consequence surface.
- `dig +short A atelierjacquelinesuzanne.fr` shows the new address.
- `MX_BASELINE=<path> npm run test:smoke -- https://atelierjacquelinesuzanne.fr` exits 0.

- Confirm the old site is gone: the homepage must no longer serve Myportfolio content.

**Section 5 — Rollback (D-06).** State the decision rule in the user's own terms: troubleshoot in place first for a bounded window rather than reverting at the first sign of trouble, but do not let it drag on indefinitely. Then make it concrete:

These are almost always a wrong webroot path, a missing `.htaccess`, or propagation lag — all fixable forward by re-running the deploy workflow, and all cheaper to fix than to revert. With the 60-second TTL from section 2, a revert stays about a minute away for the whole window.
- Rollback mechanics: restore the apex and `www` `A` records to the two Fastly addresses recorded in section 1. Note that the old site remains reachable at its Fastly origin throughout, so a revert genuinely restores the previous state.
