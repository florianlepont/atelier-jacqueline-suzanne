**The three ROADMAP success criteria this plan must produce evidence for:**
1. Visiting `atelierjacquelinesuzanne.fr` serves the new site, not the old Myportfolio site.
2. Any existing email service tied to the domain (MX records) continues to work after cutover.
3. The DNS cutover was rehearsed/verified (staging alias tested, TTLs lowered in advance) before the production switch.

Criterion 3 is already satisfied by evidence produced earlier — plan `05-04`'s staging rehearsal transcript and its deliberately-failing pre-cutover production run, plus plan `05-05` Task 2 step 6's TTL lowering with the previous TTL recorded. This plan collects that evidence rather than re-earning it.

**Verification tooling** (plan `05-04`): `scripts/launch-smoke-check.sh`, run as `npm run test:smoke -- <origin>`, env `BASE` / `SKIP_PHP` / `MX_BASELINE`. Probes: reachability across seven paths, custom-404 with the Apache `ErrorDocument` proof, site-identity string, canonical-origin check against `sitemap.xml` and `robots.txt`, PHP method guard (405), honeypot-safe POST (200 + success, sends no mail), malformed-submission rejection (400), and an MX diff against `MX_BASELINE`.

**The honeypot probe sends no mail.** It is safe to run in a loop while troubleshooting. Exactly one real message is sent in this plan, by hand, in Task 2.

**Known deliverability risk to test for explicitly:** the apex SPF record is `v=spf1 include:mx.ovh.com -all` — a hard fail. `contact.php` sends with envelope-from and `From:` both set to `no-reply@atelierjacquelinesuzanne.fr` (owned domain) precisely to survive this, but it is NOT independently confirmed that OVH's web-hosting cluster sends from inside that include. So the real message may land in spam. That is a mail-configuration issue in `contact.php`, not a DNS failure, and per runbook section 5 it does not justify a DNS rollback.

**Cross-origin check (deferred here from plan `05-02`):** `https://florianlepont.github.io/ajs-website/contact/` POSTs cross-origin to `https://atelierjacquelinesuzanne.fr/contact.php`, admitted by an exact-match allow-origin allowlist in `contact.php`. Before this cutover that request could not succeed, because the domain served the old site. It should work now. If the staging form falls through to the D-09 fallback message while the production form succeeds, the allow-origin header is the suspect.

**Rollback posture (D-06):** troubleshoot in place for a bounded window rather than reverting at the first problem — except for mail, where any MX difference is an immediate, no-deliberation revert. Rollback values are in `05-DNS-BASELINE.md`; the 60-second TTL keeps reversal about a minute away.

- **MX diff failed** — stop everything else and treat it as the immediate-rollback trigger. Restore the MX records from `05-DNS-BASELINE.md` or OVH's DNS zone version history now. Email is the higher-consequence surface and it is not a fix-forward situation.

Note that a locally cached DNS answer can lag the authoritative one, so cross-check with a public resolver: `dig +short A atelierjacquelinesuzanne.fr @1.1.1.1`.
- **Reachability passes but the 404 probe fails** — Apache is not honouring `ErrorDocument`, which almost always means `.htaccess` did not land. Confirm the second SFTP step ran in the `05-05` deploy run; re-dispatch the workflow if not.
- **Canonical-origin probe fails** (`sitemap.xml` advertising the GitHub Pages host) — the production build was made without `SITE_URL`. Fix-forward: correct `deploy-ovh.yml` and re-dispatch. Do not roll back DNS for this; the site works, its metadata is just wrong.
- **PHP probes fail** — a `405` that comes back as `200` with PHP source in the body means PHP is not executing for that path; a connection error on `contact.php` means the file did not upload. Both are fix-forward via re-dispatch.
- **Only the malformed-submission probe fails** — validation is not behaving as `tests/unit/contact-php.test.ts` asserted for the source. Compare the deployed file against the repo copy; a stale upload is the likely cause.

Every one of these except the MX case is fixable by re-dispatching the deploy workflow, which is why the ordering in `05-05` put the upload first. Iterate until the smoke check exits 0, or until a failure is understood well enough to be a recorded, accepted deviation.
