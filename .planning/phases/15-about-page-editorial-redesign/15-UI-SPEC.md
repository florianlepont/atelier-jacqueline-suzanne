## Typography

Reuse the project's existing global roles exactly. Do NOT introduce new font sizes/weights — About's redesign must fit inside this already-declared set plus the two editorial-page-specific roles already established by Contact/Éditions.

**Declared exception to the 4-size maximum (5 roles in use, all pre-existing):** This composition draws from three separate token families that already coexist in production — the global base scale (`--text-label-size` 14px, `--text-body-size` 16px, plus the unused-here `--text-heading-size` 20px / `--text-display-size` 32px), the editorial-page family (`--editorial-page-section-title-size` clamp(22–30px), `--editorial-page-lead-size` clamp(18–22px), plus the unused-here `--editorial-page-title-size` clamp(40–56px)), and `PageTitleHeader.astro`'s own hardcoded h1 rule (`clamp(64px, 9vw, 140px)` — a literal value in that component's `<style>` block, not itself a named CSS custom property). About's redesign needs 5 of these pre-existing roles simultaneously: Label, Body, Heading, Display, and Lead below. Collapsing any two would mean either (a) editing a shared component (`PageTitleHeader.astro`, used by Contact/Éditions/other detail pages) or (b) editing a cross-page token (`--editorial-page-lead-size` / `--editorial-page-section-title-size`, both already live outside About) — purely to satisfy this phase's local budget, which would fight the existing design system rather than serve it. Per this section's own opening line and REQUIREMENTS.md ABOUT-04, the actual compliance target for this phase is **zero new sizes**, which holds: every value below pre-exists in production today, and this phase introduces none. This is a bounded, explicitly-stated exception to the general 4-size guideline — not an unflagged gap.

| Role | Size | Weight | Line Height | Status | Source |
|------|------|--------|-------------|--------|--------|
| Label / eyebrow / section number | 14px (`--text-label-size`) | 400 regular | 1.5 | Pre-existing (global token) | Used verbatim by `PageTitleHeader__eyebrow` and `.about-page__number` |
| Body | 16px (`--text-body-size`) | 400 regular | 1.5 | Pre-existing (global token) | Section paragraph text (`.about-page__section p`) |
| Heading (section h2) | clamp(22px, 2.25vw, 30px) (`--editorial-page-section-title-size`) | 600 semibold, `--font-display` | 1.15 | Pre-existing (editorial-page token) | Already used by `.about-page h2` |
| Display (page title) | clamp(64px, 9vw, 140px) | 600 semibold, `--font-display` | 1.05 | Pre-existing (hardcoded in `PageTitleHeader.astro`, not a shared variable) | `PageTitleHeader h1` — supersedes About's own current `h1` rule (`--editorial-page-title-size`, clamp 40–56px) once ABOUT-03 lands. Delete the now-dead `.about-page h1` rule rather than leaving two competing title styles. |
| Lead / biography paragraph | clamp(18px, 1.5vw, 22px) (`--editorial-page-lead-size`) | 400 regular | 1.35 (`--editorial-page-lead-leading`) | Pre-existing (editorial-page token) | Per D-01, the biography keeps this exact role, just repositioned below the header instead of beside the old in-body `h1` |

Font weights used across this phase: exactly 2 (`--weight-regular` 400, `--weight-semibold` 600) — matches the project-wide 2-weight contract.

## Layout & Composition Contract

### Locked (from CONTEXT.md — not open for sketching)

- **D-01:** Biography renders as its own lead paragraph below `PageTitleHeader`, using the `--editorial-page-lead-*` typography role (see Typography table). `PageTitleHeader`'s `intro` prop stays empty.
- **D-02 / D-03:** Portrait stays circular, at its current ~112px (desktop) / 72px (mobile) scale — a small accent, never resized into a focal editorial photo, never squared/framed. Exact position within the new composition is the one open sub-question (see below).
- **D-04:** The full-bleed exhibition/gallery-install photo becomes a pinned (`position: sticky`), scroll-scrubbed shrink reveal — same mechanism as `DetailHero.astro`/sketch 005 (vanilla JS, no library). Desktop + non-reduced-motion only.
- **D-06:** Mobile viewports (`max-width: 767px`, matching the existing About/DetailHero breakpoint) keep a plain static photo band — today's treatment, unchanged. This is independent of the `prefers-reduced-motion` fallback (D-04): a desktop user with `prefers-reduced-motion: reduce` gets the settled end-state immediately (no sticky pin at all); a mobile user gets the static band regardless of motion preference.
- Existing responsive breakpoints (`767px`, `480px` in `AboutPageBody.astro`) are preserved/extended, not replaced with a new scheme. Note the existing minor inconsistency already in production: `PageTitleHeader.astro` switches its own internal grid at `760px` while `AboutPageBody.astro`/`DetailHero.astro` switch at `767px`/`768px` — this is a pre-existing, shared-component discrepancy, out of scope to reconcile in this phase (do not "fix" `PageTitleHeader`'s breakpoint as a side effect).
- Bio/practice/medium copy content is unchanged (verbatim preservation, per REQUIREMENTS.md).
- Portrait photo itself (the image asset) is not replaced — layout/treatment only (per REQUIREMENTS.md Out of Scope).

### Open — resolve via the mandatory sketch process (see next section)

- **D-05:** What the hero-photo shrink resolves into — a pure motion "settle" with no text reveal, vs. a reveal into the "01 Atelier & pratique" section using only existing markup/copy (never new text). If the "reveal into section 01" direction is chosen, budget for a `--color-accent` pink-underline treatment on at most one small element in that reveal (see Color contract), mirroring `DetailHero__format`'s existing visual language — do not invent a new accent treatment.
- **D-07:** Numbered-sections final structure — two-column restyle (closer to today's layout, re-skinned to the new rhythm) vs. a stacked full-width row-list (Éditions-style) vs. another asymmetric structure. Whichever hero-reveal target D-05 lands on may constrain this (e.g., a "reveal into section 01" treatment likely reads best if section 01 can visually anchor near the hero, favoring an asymmetric or stacked structure over a strict two-column split).
- Exact sizing/positioning of the circular portrait within whatever composition wins (shape/scale locked by D-02/D-03; placement only).

## Sketch Exploration Requirement (process contract, not a visual token)

Per ROADMAP.md Phase 15 success criterion 3 and REQUIREMENTS.md ABOUT-04, **the implemented layout direction must be chosen from multiple sketched proposals**, using the same process as `.planning/sketches/013-contact-page-composition/` (multiple variants → real feedback rounds → a named winner → then implementation) — a single unreviewed guess is an explicit failure condition for this phase.

The sketch must:
1. Produce at least 2–3 distinct layout variants exploring the D-05/D-07 open questions above, using **real production copy** (the actual bio/practice/medium text, not lorem ipsum) — mirroring sketch 013's use of real `intro`/`publicEmail`/form-field copy.
2. Stay within every locked constraint above (tokens, portrait treatment, hero mechanism, mobile/reduced-motion fallback) — sketching is for composition/rhythm, not for reopening D-01–D-04/D-06.
3. Be checked at both a "short-but-wide" desktop viewport class and mobile, per sketch 013's precedent of catching viewport-ratio-specific breakage (013's Round 1 regression) and touch-target/field-sizing issues (013's Round 3) — apply the same scrutiny here to the portrait's mobile placement and the hero's static-band fallback.
4. Record a named winner with a one-line rationale, in the same `README.md` format as sketch 005/013 (`sketch`, `name`, `question`, `winner` frontmatter + `## Variants` + `## Why {winner}` sections).

## Motion & Accessibility Contract

- **Desktop + motion-enabled (default):** hero photo pins via `position: sticky`, shrinks on scroll per D-04's mechanism; whatever D-05 resolves the reveal into fades/translates in via the same `computeProgress`/`lerp` driver pattern as `DetailHero.astro`.
- **Desktop + `prefers-reduced-motion: reduce`:** no sticky pin, no scroll-linked motion at all — the settled end-state (final shrink width, final reveal opacity/position) renders immediately via CSS media query, exactly matching `DetailHero.astro`'s `@media (prefers-reduced-motion: reduce) and (min-width: 768px)` block. This is a site-wide convention (HomeCarousel, Lightbox View Transitions, `DetailHero.astro`) — do not deviate.
- **Mobile (`max-width: 767px`), any motion preference:** static photo band, no pin, no scroll listener attached at all (matches D-06; mirrors `DetailHero.astro`'s own `@media (max-width: 767px)` block, which applies "regardless of motion preference").
- All new interactive/focusable elements (if D-05's resolution introduces any, e.g. an anchor into section 01) must carry visible `:focus-visible` treatment consistent with the project's existing `outline: 2px solid var(--color-accent); outline-offset: var(--focus-ring-offset);` convention (see `DetailHero__trigger:focus-visible`).
- No new scroll-jacking gesture (e.g. `DetailHero.astro`'s upward-overscroll-to-return gesture) is in scope for this phase — do not port that behavior; it is specific to gallery detail pages returning to the homepage carousel and has no About-page equivalent in CONTEXT.md.
