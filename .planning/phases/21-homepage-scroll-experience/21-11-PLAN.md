<objective>
Close `21-UAT.md` round-2 gap 4 (`.planning/debug/homepage-scroll-still-not-fullscreen.md`): replace the deck's rigid `100svh` sizing with a live-synced `--deck-vh` custom property driven from `window.visualViewport`, so every full-screen deck section covers the CURRENT viewport in every intermediate Mobile Safari toolbar state.

Purpose: plan 21-09 optimised for the wrong constraint. `100svh` is statically bound to Safari's SMALLEST content area (toolbar fully expanded). It guarantees a box is never LARGER than the screen and thereby guarantees it is often SMALLER — specifically, smaller by exactly the height of the retracted chrome, which is the normal majority-of-the-time state while a visitor is actively scrolling a natively-scrolled document. The uncovered strip falls through to `body { background-color: var(--color-dominant) }` (literal white), which is the reported white bar at the top AND the newly-reported white gap at the bottom. The codebase's own cited precedent, `.home-hero__photo`, never used an exact `height: 100svh` — it uses `min-height: 100svh; max-height: 100vh`, a RANGE. Plan 21-09 borrowed the unit but not the shape.

This plan lands FIRST in the gap-closure set on purpose: plans 21-12 (post-zoom dead zone) and 21-13 (pinned intro redesign) both add or move full-screen deck boxes, and both must be built on the corrected viewport-height convention rather than each re-learning that `100svh` undershoots.

Output: a self-contained viewport-height sync block plus the CSS conversion in `src/components/HomeCarousel.astro`, and new convention cases in `tests/e2e/homepage-scroll-deck.spec.ts`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser-reported viewport metrics -> CSS custom property | `window.visualViewport.height` / `window.innerHeight` are read from the user agent and written into a style property that governs layout. Values are numeric and browser-owned; they are formatted into a px string, never interpolated into a selector, a URL, or markup. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-11-A | Denial of Service | Per-frame custom-property write forcing synchronous layout | medium | mitigate | Writing `--deck-vh` changes the height of five full-screen boxes; the very next `getBoundingClientRect()` in the same frame then forces a synchronous layout. Unbounded, that is a forced reflow at 60Hz plus battery drain on the exact device class this phase targets. Mitigated by the 1px change-detection cache (Task 1 item 2): on a stationary or steadily-scrolled page the viewport height does not change, so no write and no extra reflow occurs — the loop's existing "zero style writes when stationary" invariant (T-21-07-A) is preserved. |
| T-21-11-B | Tampering | Pinch-zoom shrinking every deck box mid-gesture | low | mitigate | `visualViewport.height` reports the zoomed-in visible area under pinch-zoom, which would collapse every full-screen section to a fraction of the screen while the visitor is zoomed in. Mitigated by the scale guard (Task 1 item 2), which falls back to `window.innerHeight` whenever the visual viewport is scaled beyond ~1.01. |
| T-21-11-C | Tampering | The sizing property surviving the motion driver's detach | low | mitigate | If `clearInlineStyles()` removed `--deck-vh`, a reduced-motion or desktop-gate detach would silently drop the deck back to the undersized `100svh` path — reintroducing gap 4 for exactly the visitors D-15 protects. Mitigated by deliberately excluding it from that removal list (Task 1 item 5) and by Task 3 case 4 asserting the property survives reduced motion. |
| T-21-11-D | Information Disclosure | Viewport metrics written into the DOM | low | accept | The visible viewport height is already trivially observable by any script on the page and is not user data. No new sink; the value is number-formatted into a px string on a style property. |
