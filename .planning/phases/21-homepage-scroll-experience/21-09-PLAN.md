<objective>
Close UAT gap 4 (the white bar near the iPhone status bar): stop sizing the phone-width deck against the live dynamic-viewport unit, adopt the same real-device-validated convention the sibling full-bleed hero already uses, give photo-bearing surfaces a non-white paint floor, and give Mobile Safari an explicit phone-width theme colour so it stops deriving the chrome-adjacent strip from the page's white body background.

Purpose: `21-UAT.md`'s fourth gap has a confirmed root cause. The deck (plans 21-04/21-05) sizes its track, its pinned stage, its wordmark padding and every slide against the dynamic viewport-height unit exclusively — while `.home-hero__photo`, one section over in the same file, deliberately does NOT, and carries an authored comment explaining the real-device screenshot that motivated the choice: Mobile Safari's viewport-height units do not resize dependent boxes in lockstep with the toolbar's collapse/expand animation, and the small-viewport unit (the worst case, chrome visible) is the one that behaves. `DetailHero.astro`'s own desktop scroll track already uses the exact `calc(100svh + 900px)` shape this plan adopts, so the formula has in-repo precedent as well as in-repo justification. Compounding it, the site has no `theme-color` meta anywhere, so during that same toolbar-animation window Safari colours the strip from `body`'s background, which resolves to literal white.

Two things this plan deliberately does NOT do, with reasons recorded rather than left as silent omissions:

- **No `viewport-fit=cover`.** The debug session notes its absence, but adding it opts the WHOLE SITE into rendering under the status bar and would require `env(safe-area-inset-*)` padding on every page's chrome — a site-wide layout change with a blast radius far beyond this gap, on a milestone whose UI-02 constraint is that nothing outside phone-width homepage may change. The gap's own `missing` list asks for the viewport-height strategy and the theme colour, not for `viewport-fit`.
- **No per-slide dynamic theme-colour swap.** The gap lists it as "possibly"; it is rejected on purpose. The strip should read as part of the photograph, and the per-slide accents are bright saturated hues — swapping the browser chrome to a different bright colour at every arrival would be more visually disruptive than the white flash it replaces, and would add a write to a per-frame loop for a value only the OS chrome consumes.

The paint floor is applied only to surfaces a photo already covers (each slide, and the crossfade photo layer), never to the pinned stage or the deck root. That is deliberate: the pre-zoom wordmark screen keeps today's exact white appearance, so neither the unsupported-engine wordmark fallback colour nor the photo-load-failure fallback that `critical.smoke.spec.ts` guards has its contrast changed. A white strip over a white screen is invisible anyway — the bar is only noticeable against a photo, which is exactly where the floor goes.

D-01, D-02, D-05 and D-08 are all preserved: the sticky pin, the snap deck and the scroll-past-into-the-footer behaviour depend on the track/stage delta and the per-slide height being one viewport tall, both of which this plan keeps true with a different unit.

Output: CSS changes in `src/components/HomeCarousel.astro`, a new optional prop plus meta tag in `src/layouts/BaseLayout.astro`, one line in each homepage route file, and new cases in `tests/e2e/homepage-scroll-deck.spec.ts`.
</objective>
