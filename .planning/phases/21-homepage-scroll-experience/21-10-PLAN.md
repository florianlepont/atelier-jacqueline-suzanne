<objective>
Close UAT gap 1 (the missing pre-zoom intro beat): give the phone-width homepage a two-beat opening — a centred logomark with a scroll-down cue, then the site's intro tagline arriving beneath it — before the wordmark zoom that currently opens the page.

Purpose: `21-UAT.md`'s first gap is explicitly a SCOPE gap, not a defect. None of `21-CONTEXT.md`'s sixteen locked decisions specifies a pre-wordmark beat; D-01/D-15 name the wordmark itself as the opening element, and the implementation built exactly that. The developer's real-device feedback asks for a three-beat opening instead. The debug session confirms the insertion is structurally cheap: `computeZoomProgress` derives progress from the track's own live bounding rect rather than a document-relative offset, so prepending siblings before `.home-scroll-deck__track` requires no change to `ZOOM_REVEAL_DISTANCE`, the track height calc, or any zoom math — the zoom simply stays at its rest state until the track's own top edge reaches the viewport top. Both pieces of content already exist in the component's own scope: `introBody` (from `resolveHomepageIntro`, currently rendered only into the desktop/tablet-only intro paragraphs) and `logoWhiteSrc`/`logoBlackSrc` (already computed locally with the base-aware asset pattern). No Sanity schema work, no new data fetch, no new prop threading.

The gap names two structural frictions this plan owns: extending D-12's header hide, which is currently wired solely to `data-zoom-active` and would otherwise show the small top-left header logo simultaneously with a new large centred logo; and deliberately rewriting `21-04-PLAN.md` Task 1 case 3's now-conflicting assertion that the wordmark fills the screen "before any scrolling" — a preceding beat necessarily makes that literally false BY DESIGN, so it is rewritten, not chased as a regression.

This is the last plan of the gap-closure set, so its final task carries the real-device human check covering all four `21-UAT.md` gaps at once.

Output: new markup and CSS plus a driver extension in `src/components/HomeCarousel.astro`, and reworked plus new cases in `tests/e2e/homepage-scroll-deck.spec.ts`.
</objective>

<assumptions>
## Labelled assumptions — every one of these is a genuine open question the developer may correct

`21-UAT.md` gap 1's `missing` list explicitly records that "fresh discuss-phase-style decisions" are needed and names several unresolved questions. No locked decision covers them. Rather than invent answers silently, each is stated here with its reasoning so it can be overridden before or during execution. **If the developer changes any of these, only the specific task item it names needs revising — none of them changes the plan's shape.** The executor MUST restate these five assumptions verbatim in `21-10-SUMMARY.md` under a heading that makes clear they were assumptions and not decisions, and the real-device human check in Task 3 asks the developer to confirm or correct each one by name.

- **A1 — Reduced motion gets the intro beats, as static content.** Both beats render; the tagline is permanently visible (no reveal); the scroll cue's motion is suppressed; and the header is NOT hidden during the beats. Reasoning: the beats are *content*, not motion, so excluding a reduced-motion visitor from them would hide real information; but D-15's established convention is that no scroll-linked JS attaches at all under that query, and the header hide is JS-attribute-driven, so the header staying visible falls out of that convention rather than being a new choice. This also keeps the suite's existing reduced-motion route to an interactive header intact — `mobile-nav.spec.ts`, `accessibility.spec.ts` and `critical.smoke.spec.ts` all rely on it. *Alternative if corrected: hide the header under reduced motion too, which would require a CSS-only (non-JS) hide condition and a coordinated update to those three specs.*

- **A2 — The beats are dismissed by scrolling past them, and nothing else.** No tap-to-dismiss, no skip button, no timed auto-advance. Reasoning: every other state in this deck is a pure function of scroll position (D-04's reversibility depends on exactly that), so a tap or timer dismissal would introduce a second, one-way interaction model and a piece of state the rest of the deck does not have — including the question of what happens when the visitor scrolls back up. Scroll-past keeps the whole opening reversible, which is consistent with D-04. *Alternative if corrected: a tap-to-dismiss would need a decision about whether scrolling back up restores the beats.*

- **A3 — The intro beats get NO scroll-snap point of their own.** Reasoning: each beat is exactly one viewport tall, so an ordinary scroll already lands cleanly on it without help. Adding `scroll-snap-align` immediately before the deliberately snap-free 900px zoom scrub would put a snap target right where the scrub begins, and the page-wide `proximity` snap could then pull the visitor backwards into the intro mid-scrub — the same conflict class `21-RESEARCH.md` Pitfall 6 made the track itself snap-free to avoid. The slides keep their own `scroll-snap-align: start` plus `scroll-snap-stop: always` unchanged. *Alternative if corrected: giving the beats snap points requires re-testing the scrub against proximity snap on a real device.*

- **A4 — Two stacked full-viewport sections in normal flow; no new pinned or scrubbed machinery.** The pre-zoom distance is therefore two viewport heights. Both beats render the logomark at identical size and position, so scrolling from beat 1 to beat 2 reads as the tagline arriving beneath a logo that appears to stay put — which is what the developer's wording describes ("then the site's intro tagline appears below the logo, then that disappears"), achieved without a second sticky/scrub driver. Reasoning: adding another pinned scroll-scrubbed stage would add a second handoff boundary, and handoff desynchronisation is precisely the defect plan 21-07 just fixed. *Alternative if corrected: one pinned intro section whose tagline scrubs in, which is a materially larger change.*

- **A5 — Visual treatment: ink background, white logomark, a short localised scroll cue with a gentle vertical drift.** Reasoning: the deck's own paint floor is the ink token (plan 21-09) and its phone theme colour is the same value, so an ink intro screen is continuous with everything that follows and avoids reintroducing the white-strip problem plan 21-09 just closed; a white logomark is required for contrast on ink, and `logoWhiteSrc` already exists for exactly that. The cue label uses the existing hardcoded locale-conditional string idiom this component already uses elsewhere, so no new CMS field is introduced. *Alternative if corrected: a white intro screen with the black logomark, which matches the site's dominant identity but reintroduces the white-strip exposure at the top of the screen and diverges from the theme colour.*
</assumptions>
