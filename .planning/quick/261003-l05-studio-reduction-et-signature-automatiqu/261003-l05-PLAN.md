Facts established while planning (do not re-derive; they were read from the installed sanity 6.6.0 bundle `sanity/node_modules/sanity/lib/_chunks-es/index2.js`, the `@sanity/types` typings and the repo):
- Schemas: every image field is a plain `type: 'image'` (about page images, SEO share image, exhibition image, edition `images[]`, gallery `images[]`). No schema sets `options.sources`, `options.accept` or custom `components.input` on an image, so a global config-level mechanism covers all of them without editing any schema. Gallery and edition photos are array members: the ARRAY field (not the image input) handles dropped files, which is why a per-image `components.input` wrapper cannot intercept them.
- The default image asset source is created by the Studio as `{name: 'sanity-default', component, icon, Uploader}` where `Uploader` is a class closing over the Studio client. With the Media Library not enabled, `form.image.assetSources` receives `prev = [thatSource]`. As a function, the resolver has the shape `(prev: AssetSource[], context) => AssetSource[]` (type `AssetSourceResolver`).
- Uploader contract (`AssetSourceUploader`, exported with `AssetSource` and `AssetSourceUploaderClass` from 'sanity'): methods `upload(files, {schemaType, onChange}): AssetSourceUploadFile[]`, `abort(file?)`, `getFiles()`, `subscribe(subscriber): () => void`, `updateFile(id, data)`, `reset()`. Events: `{type:'progress'|'status'|'abort'|'error'|'all-complete', ...}`; `AssetSourceUploadFile` is `{id, file, progress, status: 'pending'|'uploading'|'complete'|'error'|'aborted'|'alreadyExists', error?, result?}`. The default Uploader resolves the internal image uploader per file and emits patches through `onChange`; it emits `all-complete` then resets itself when every file is complete/error/aborted, and it only does so when it holds at least one file.
- Exactly two call sites instantiate an Uploader: `useAssetSourceUploader` (single image/file inputs: button, drop on the field, paste) and the array field `handleSelectFile` (one call PER dropped file, so a 40-photo drop creates 40 Uploader instances at once). Both subscribe before calling `upload` and ignore its return value. On unmount or Cancel they call `uploader.abort()` and the `subscribe` unsubscribe function. When more than one differently named upload-capable source exists the Studio asks for an upload destination, hence "wrap in place, never add a source".

Design decisions taken (planner discretion, record them in the SUMMARY):
1. LONGEST side, not width. `maxDimension` caps max(width, height). The offline script caps width only, so a 4000x6000 portrait becomes 2400x3600 there (8.6 MP) but 1600x2400 in the Studio (3.8 MP). The point of the cap is deterrence and storage, so portraits must be capped like landscapes; the site never needs more than 2000 px wide. The doc states this difference explicitly.
2. Interception point: wrap the default dataset asset source's Uploader through the global `form.image.assetSources` resolver. Rejected: a per-field `components.input` wrapper (the Studio's image input re-injects `assetSources` and `resolveUploader` after any custom input, and array-dropped files never pass through an image input), and a global `form.components.input` (same problem, plus it would sit in every field's render path). The Uploader is the only choke point both call sites share, it adds no UI, and it keeps keyboard and ARIA behaviour intact by construction.
3. Quality 0.9, matching the offline script's 90. PNG stays PNG (lossless, no surprise artefacts on graphics), WebP stays WebP; if the browser returns a different MIME type than requested (Safari encodes WebP requests as PNG), that is treated as a failure and the original is uploaded with a warning.
4. Re-encode whenever the master switch is on, the MIME type is supported, and (a resize is needed OR the signature is enabled). With the signature on (default) every JPEG/PNG/WebP is therefore re-encoded and its EXIF/IPTC/GPS stripped (intended privacy benefit). With the signature off, an image already within `maxDimension` is left byte-for-byte untouched (so it keeps its EXIF); this is documented, not hidden.
5. Robustness additions that cost a few lines and prevent real failures: module-level serial queue (concurrency 1), 30 s processing timeout inside the queued task, 100 MB input-size guard, abort support while queued or processing, idempotent wrapping, notice batching (flush on queue idle, plus a 6 s maximum wait).
6. No new dependency. Canvas, `createImageBitmap` and `toBlob` are built into every browser the Studio supports. `pica` or `browser-image-compression` were considered and rejected: extra supply-chain surface and bundle weight for a quality gain that `imageSmoothingQuality = 'high'` already covers at 2400 px. Revisit only if manual check 1 shows aliasing.
7. Test placement: pure/glue `.ts` tests live in ROOT `tests/unit/` (the root coverage includes `sanity/editorial/**/*.ts`; precedent workflow-logic.test.ts and studio-site-url.test.ts); only the `.tsx` bridge is tested inside the Studio project, which is where the per-file TSX coverage floor applies.
8. File naming avoids a case-insensitive collision: the notice pub/sub is `uploadNoticeChannel.ts`, never a lowercase twin of `ImageUploadNotices.tsx`.
9. Task 3 lists six files, but three of them are a few lines each (the StudioLayout mount, the README paragraph, the two matrix rows). Splitting further would make a fourth task, which the brief forbids; the docs stay last so they describe what was actually built.
