<objective>
Fix a third real, screenshot-reported, already-root-caused gap on the deployed Éditions overview header (sketch-012 F1, from quick tasks 260728-lbh + 260728-nj7). Florian reported the vertical space between the site's top navigation and the 'ATELIER JACQUELINE SUZANNE' / 'Éditions' title block is too large. This is a DIFFERENT gap than 260728-nj7 fixed (that was the header-block-to-row-list gap below the title; this is the site-nav-to-title gap above it).

Root cause (live-diagnosed on the deployed page at 1440px, not guessed): the site header ends at y≈148.9px and `.editions-list` (the `<article>` wrapping the whole page body) immediately begins there with a computed `padding-top: 96px`, placing the eyebrow at y≈244.9px — a 96px gap of pure whitespace above a now-much-larger h1 (clamp(64px, 9vw, 140px), enlarged in 260728-lbh), with nothing occupying it (unlike About, whose equivalent space is filled by a portrait image). The 96px comes from the SHARED token `--editorial-page-padding-block: clamp(48px, 7vw, 96px)`, which is ALSO used by About and Contact — so it must NOT be changed globally.

Fix (Éditions-scoped override, live-tested on the deployed page): split `.editions-list`'s `padding` shorthand into three longhand declarations and cap only the TOP padding with its own lower-ceiling clamp — same minimum (48px) and slope (7vw) as the shared token, but a 56px ceiling instead of 96px:
- `padding-inline: var(--editorial-page-padding-inline);` (unchanged value, just un-shorthanded)
- `padding-top: clamp(48px, 7vw, 56px);` (Éditions-specific — caps the desktop gap at 56px)
- `padding-bottom: var(--editorial-page-padding-block);` (unchanged shared token — bottom spacing was fine)

Live-verified before choosing: at 1440px the override drops padding-top 96px->56px (screenshot showed the title sitting noticeably closer to the nav, reading as tight and well-proportioned); at 800px it is a no-op (56px->56px); at 375px it is a no-op (48px minimum unchanged). Halftone and entrance animation are unaffected — neither depends on this padding value.

Purpose: correct the visible over-large nav-to-title gap Florian flagged, exactly as diagnosed and live-verified, WITHOUT altering the shared spacing token (so About and Contact stay exactly as they are) and without touching anything else in the approved sketch-012 F1 design.
Output: one shared component edited — one declaration split into three (one new capped value) — one commit.
</objective>

`padding: var(--editorial-page-padding-block) var(--editorial-page-padding-inline);`
with these THREE longhand declarations, in this order:

Why each line:
- `padding-inline` keeps the horizontal padding byte-identical to before (the shorthand's second value) — no horizontal change whatsoever, just un-shorthanded so the vertical axis can be split.
- `padding-top: clamp(48px, 7vw, 56px)` is the actual fix: same minimum (48px) and same 7vw slope as the shared `--editorial-page-padding-block` token, but a 56px ceiling instead of 96px. Live-measured on the deployed page: at 1440px this drops the computed padding-top from 96px to 56px (tighter, well-proportioned, not cramped); at 800px it is a no-op (the 7vw slope already resolves to 56px there, and 56px <= the 56px cap); at 375px it is a no-op (48px minimum unchanged). Because it is a clamp ratio, it holds correctly at every viewport — do NOT substitute a fixed pixel value.
- `padding-bottom: var(--editorial-page-padding-block)` keeps the bottom padding on the unchanged shared token — nobody complained about bottom spacing, so it stays exactly as it was.

Every other property on the `.editions-list` rule stays byte-identical: `width: min(100%, var(--editorial-page-max));` and `margin: 0 auto;`.
