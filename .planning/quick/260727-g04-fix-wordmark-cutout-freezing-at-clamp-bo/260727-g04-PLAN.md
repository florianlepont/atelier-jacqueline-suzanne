<objective>
Fix the hero photo-cutout wordmark visibly freezing (pinned at its clamp boundary, e.g. `--wordmark-bg-position: -804px`) for the entire ~420-480ms of `commitEdge()`'s edge-click full-slide commit, while the hero photo slides the full viewport width underneath it.

This is a confirmed, live-measured bug (do NOT re-diagnose — see the task brief's frame-by-frame data). It is distinct from everything fixed in quick-260727-bsm/drq/fc2. Root cause: quick-260727-drq's Bug 2 clamp in `computeWordmarkBackgroundPosition()` correctly pins the wordmark sample to the photo's real pixel bounds `[-804, 0]`, but `commitEdge()` pushes `--peek-shift` to ±100% (vastly beyond the ~16% hover-peek range the clamp was validated against). The raw position blows past the boundary almost immediately and stays there for nearly the whole slide, so the clamp holds the output frozen at -804 — visually "the picture inside the font does not follow."

Fix: apply the same "go solid, then reveal" beat that EVERY other navigation path already uses. `render()` unconditionally removes `has-wordmark-photo` + sets `--wordmark-photo: none` at its very start (solid-ink fallback), then re-establishes the cutout via `revealWordmarkPhoto()` once the new photo loads. Apply that reset at the START of `commitEdge()`'s full-slide commit so the wordmark settles into neutral ink for the slide's duration, instead of holding a frozen, wrongly-cropped slice of the departing photo. `finish()`'s existing `render()` call still re-reveals the cutout with the new photo's correct alignment once the swap lands — no change there.

Purpose: make the commit's full-slide visually coherent with the rest of the site's navigation language, and stop the "frozen cutout" read.
Output: a one-liner-scale behavioral change in `commitEdge()` plus a FR+EN e2e regression test proving the wordmark goes solid mid-slide and re-reveals realigned at settle.
</objective>
