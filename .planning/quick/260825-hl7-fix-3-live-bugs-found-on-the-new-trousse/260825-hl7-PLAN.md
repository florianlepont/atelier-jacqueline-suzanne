<decisions>
Three design calls made during planning — carry these into the SUMMARY:

**D-1 — Shared function, not duplicated-array-with-drift-test.** `src/lib/site-config.ts` gets the single palette definition and `home-carousel-runtime.ts` imports it. Rejected alternative (keep two arrays + a byte-identity unit test) is strictly worse here because the safe-to-import precondition is confirmed, not speculative: `site-config.ts`'s only import is an erased `import type`, and the runtime already imports `../lib/home-carousel`.

**D-2 — The shared palette keeps CSS custom-property REFERENCE strings (`'var(--color-accent)'`), it does not resolve to hexes.** `--color-accent` is `--pink-600` = `#D6327C`, which is NOT `HERO_COLORS.pink` (`#FF3B94`) — any hex-ification would silently change the homepage's shipped rendering, and the homepage is the correct side of this bug. Passing the same `var(...)` string through `page-models.ts` into `.detail-hero`'s inline custom property makes both pages resolve against the same `:root` tokens, byte-identically. Consequence: the automatic path takes its text color from the palette entry's own `text` field and must NOT be routed through `getHeroTextColor()` (which cannot parse a `var()` string and would return ink). `getHeroTextColor()` stays in use for the explicit-`heroColor` path only.

**D-3 — `homeIndex` is a REQUIRED parameter of `buildGalleryDetailModel`, not optional-with-default.** A default would let a missing locale-route wiring silently degrade to palette entry 0 with no signal; required makes `npm run typecheck` fail loudly if either `[slug].astro` is not updated. Existing `tests/unit/page-models.test.ts` call sites get updated accordingly.
</decisions>
