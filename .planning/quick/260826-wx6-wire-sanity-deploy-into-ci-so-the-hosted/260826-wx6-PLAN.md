<objective>
Make the hosted Sanity Studio (https://atelier-jacqueline-suzanne.sanity.studio/) redeploy automatically from CI, so its bundle can never drift behind the repository again.

Today `sanity/package.json` has a `deploy` script (`sanity deploy`) that no workflow ever invokes. Publishing the Studio is a purely manual, easily-forgotten local CLI act. That gap produced a real, user-visible failure this session: today's `ajs-website` -> `atelier-jacqueline-suzanne` rename correctly updated `SITE_PREVIEW_URL` in `sanity/editorial/deployment.ts` in source, CI went green, the site deployed fine — and the live Studio kept serving a months-old bundle with the dead pre-rename GitHub Pages URL baked in. Romane's "Voir sur le site" button sent the user to a 404. It was fixed by running `sanity deploy` by hand (see `.planning/debug/resolved/preprod-site-404-after-rename.md`).

The fix is one new step in `.github/workflows/deploy.yml`, plus the regression test and documentation that keep it honest.

Purpose: remove a manual step that has already failed once, in a project whose explicit posture is near-zero maintenance.
Output: an auto-publishing Studio, a test that fails if the step is removed or reordered, README documentation of the one-time secret setup, and a human checkpoint where Florian adds that secret and confirms the end-to-end behaviour.
</objective>

<decisions>
Three design decisions are LOCKED for this task. Do not re-litigate them during execution; if implementation reveals one is impossible, stop and report rather than silently substituting an alternative.

**D-01 — Placement: the Studio publish is the LAST step of the `build-and-deploy` job, after `Deploy to GitHub Pages`.**
Rationale: the Studio's `SITE_PREVIEW_URL` points at the GitHub Pages site, so the two should move together; publishing the Studio only once the site it links to has actually shipped keeps them in lockstep. Placing it last also inherits every blocking gate for free — Studio lint/coverage/build/typecheck, root lint/typecheck, both artifact verifications, Playwright, and Vitest coverage all already stand between the job start and this step, with no new `needs:`/`if: success()` plumbing.

**D-02 — Trigger: `if: github.event_name == 'push'`, with NO `sanity/**` paths filter.**
The Studio republishes on every push to `main`, not only on pushes that touch `sanity/`. Tradeoff, accepted deliberately and to be recorded in README:
- Cost is near-zero. `npm --prefix sanity run build` already runs on every push inside the composite action; the marginal cost here is the rebuild plus upload, roughly half a minute of runner time. `sanity deploy` is idempotent.
- A paths filter would cost more than it saves. It needs either a new third-party action (`dorny/paths-filter`, which then has to be SHA-pinned and maintained) or hand-rolled `git diff` logic against `github.event.before` — which is unreliable on force-pushes and first pushes, where that ref is all zeros.
- Most importantly, a `sanity/**` filter would reintroduce exactly the risk being removed: the Studio bundle's correctness depends on things outside `sanity/` too (the GitHub Pages base path in `deploy.yml` determines what URL the Studio should be pointing at). Trading a guaranteed-fresh Studio for thirty seconds of CI is the wrong trade for this project.
- `repository_dispatch` (`sanity-content-published`) runs are excluded because a content publish cannot change Studio source code; republishing an identical bundle on every content edit would be pure waste.

**D-03 — Missing-secret behaviour: warn-and-skip, not fail.**
When `SANITY_AUTH_TOKEN` resolves empty, the step emits a GitHub Actions warning annotation naming the secret and the setup location, then exits successfully. When the token IS present and the publish fails, the step fails the run.
Rationale: Claude cannot create repository secrets, so this workflow change necessarily lands in a commit BEFORE the secret exists. A hard guard would turn `main` red on the very next push and block the site deploy for a setup step that is not yet possible. Note this is a DELIBERATE divergence from the fail-loud `Guard: SFTP credentials are present` pattern in `deploy-ovh.yml` — that guard protects an irreversible production upload; this one protects an idempotent, re-runnable publish. Document the divergence in the step comment so a future reviewer does not "correct" it.
</decisions>
