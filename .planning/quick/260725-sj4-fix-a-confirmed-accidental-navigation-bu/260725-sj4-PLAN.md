<objective>
Fix a confirmed accidental-navigation bug in the homepage carousel's scroll-to-open gesture. On the currently-shipped code, ANY ordinary scroll on the default carousel view — a single hesitant mouse-wheel nudge or one natural touch swipe — silently navigates the visitor to a gallery detail page from a fresh page load, with no prior interaction.

Root cause (confirmed by reading the actual code): quick-260725-dcg (Fix 1) added `body:has(.home[data-display-mode='carousel']) footer.chrome-band { display: none; }`, hiding the footer entirely in carousel mode. That removed the ONLY scrollable content below the hero, so `document.documentElement.scrollHeight` equals `window.innerHeight` at load. The scroll-to-open `atBottom()` gate is therefore TRUE from first paint at scrollY 0 — before the visitor scrolls at all — defeating the "only accumulate once genuinely at the bottom" safety property (quick-260725-cfm D1/D2). Combined with quick-260725-pit's light 150px threshold, a couple of ordinary scroll deltas cross it immediately.

THE FIX: remove that one CSS rule. Restoring the footer to rendering normally in carousel mode reinstates genuine scrollable distance below the hero, so `atBottom()` only becomes true after the visitor has actually scrolled down past the hero and the footer — the real gate the 150px accumulation was always designed to sit on top of. This also better satisfies the user's original pre-dcg feedback ("put [the footer] at the end of the page, on the end of the scroll"): the footer becomes a genuine "you've reached the end, keep going a little to open" waypoint.

Do NOT re-add any visible hint (stays silent per pit). Do NOT change OPEN_OVERSCROLL_THRESHOLD (stays 150 — the vacuous gate was the problem, not the light threshold). Do NOT touch the progress-dash fill (dcg Fix 3), DetailHero.astro, or grid-mode behavior.

Purpose: stop ordinary scrolling from stealing navigation, without regressing the intended scroll-to-open feature or the silent-gesture decision.
Output: an updated `HomeCarousel.astro` (one CSS rule removed) and updated e2e specs (footer-hidden assumptions reverted + NEW fresh-load regression coverage for the actual bug).
</objective>

**Footer height / atBottom() math (confirms the fix closes the gap — not assumed):**
- The footer `footer.chrome-band` (BaseLayout.astro line 210) is a single flex row: `.footer-text` + `.footer-legal-nav` (mentions légales / confidentialité). Padding is `var(--space-lg) var(--space-md)` (24px top+bottom) base, `var(--space-xl) var(--space-md)` (32px top+bottom) at ≥768px; content ≈ one 14px/1.5 line (~21px) + 1px border. Rendered height ≈ ~85px desktop, taller on wrapping mobile.
- On the homepage, `.home-hero__photo` is `min-height:100svh` so the hero fills the viewport; the footer sits entirely below it. With the footer VISIBLE, body scrollHeight = innerHeight + ~85px, so at scrollY 0: `innerHeight + 0 >= scrollHeight - 4` → `innerHeight >= innerHeight + 85 - 4` → FALSE. atBottom() is correctly false at load. With the footer HIDDEN (current bug), scrollHeight == innerHeight → atBottom() TRUE at scrollY 0. Removing the rule flips atBottom() back to false at load — exactly the property the bug violated.
- Why "two 80px ticks" from a fresh load cannot navigate once fixed: the accumulator only adds delta when atBottom() is true. From scrollY 0, the first tick(s) are "spent" scrolling toward the footer WITHOUT accumulating (atBottom false); only ticks fired while already pinned at the bottom accumulate. A couple of ordinary ticks reach the footer and stop, with the accumulator at ≤ one tick (< 150). Navigation needs a deliberate sustained push AT the bottom.
