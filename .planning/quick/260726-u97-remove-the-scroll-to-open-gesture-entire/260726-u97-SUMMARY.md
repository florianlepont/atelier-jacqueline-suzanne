# Quick Task 260726-u97: Remove scroll-to-open gesture, replace with sketch 008 hover navigation Summary

**Deleted the homepage carousel's scroll-to-open gesture (accumulator, threshold, idle-decay watchdog, pull-scale/darken feedback, down-chevron cursor) in full and replaced it with sketch 008 Variant C's explicit hover interaction: a permanent OUVRIR/OPEN center cursor ring that morphs into an accent-tinted directional pill at 22% edge zones, a parallax-push peek of the adjacent gallery's real photo, and click-to-navigate — with a plain-tap mobile fallback composed into the existing swipe detection.**

## Decisions Made

### Footer-hide simplification (explicitly requested documentation)

`body:has(.home[data-display-mode='carousel']) footer.chrome-band { display: none; }` (the `is:global` rule, quick-260726-obg) is **kept exactly as-is, untouched**. Its original risk — `atBottom()` being vacuously true at `scrollY: 0` once the footer was hidden and no other scroll distance existed below the hero (the bug quick-260725-sj4 found and fixed) — **cannot recur**, because this task deleted `atBottom()` and every other piece of code that ever read scroll position to trigger navigation. The footer-hide is now a plain CSS rule with zero JS coupling: nothing watches scroll, so there is nothing left to make vacuously true. This is a genuine, deliberate simplification, not a re-introduction of the old risk under a different name — stated plainly here per the plan's explicit requirement. The pre-existing footer-visibility e2e tests (`footer visibility by display mode (quick-260726-obg)`, both full-bleed-hero `footer.toBeHidden()` tests) were left unchanged since they test pure CSS scoping, unrelated to gesture safety.

### What was deleted / kept / reverted (explicitly requested documentation)

**Deleted (script):** constants `OPEN_OVERSCROLL_THRESHOLD`, `BOTTOM_EPSILON`, `RESET_IDLE_MS`, `OVERSCROLL_DECAY_MS`; state `overscrollAccum`, `lastOverscrollTs`, `decayRaf`, the old `navigating` guard; functions `atBottom()`, `setPullFeedback()`, `decayOverscroll()`, `registerDownwardIntent()`, `navigateToCurrent()`; the idle-decay `setInterval` watchdog; the window-level `scroll`, `wheel`, and overscroll `touchstart`/`touchmove` listeners.

**Deleted (markup + CSS):** `.home-hero__pull-overlay` element and every rule referencing it; `--pull-scale`/`--pull-darken` custom properties and their consumers (the `transform: scale(var(--pull-scale,1))` on `.home-hero__img`, the pull-specific reduced-motion overrides); the `.home-hero__photo.is-opening ... .home-hero__pull-overlay { transition: none }` hook (deleted in Task 1, **repurposed** in Task 4 as `.home-hero__photo.is-opening .home-hero__img, .home-hero__peek { transition: none }` for the new feature's own commit-reset needs); `.home-hero__photo`'s `background-color: #000` (was pull-edge cover, now dead); the down-chevron data-URI `cursor` on `.home-hero__photo` (fully superseded by the new JS cursor).

**Kept unchanged:** the horizontal-swipe touchstart/touchend handlers (`SWIPE_MIN_DISTANCE`/`SWIPE_DIRECTION_RATIO`/`detectSwipeDirection`) except the touchend handler gained a tap-to-open branch (Task 5); keyboard arrow nav; progress-dash click nav; auto-advance/pause + progress-dash fill; the title's own click listener (`setCrossDocPhoto`) + href + mode-toggle view-transition morph; accent panel/wordmark/caption visuals; the blur-up crossfade; `tests/e2e/i18n.spec.ts` and `tests/e2e/legal.spec.ts` (untouched).

### How mobile tap-to-open composes with the existing swipe detection (explicitly requested documentation)

No second touch listener was added. The **existing** `touchend` handler on `.home-hero__photo` (the one that already computes `detectSwipeDirection(deltaX, deltaY, SWIPE_MIN_DISTANCE, SWIPE_DIRECTION_RATIO)` for horizontal swipe nav) gained one new branch, evaluated only after the swipe checks:

```js
if (direction === 'next') { goToNext(); return; }
if (direction === 'prev') { goToPrev(); return; }
if (Math.abs(deltaX) <= TAP_MAX_MOVEMENT && Math.abs(deltaY) <= TAP_MAX_MOVEMENT) { openCurrent(); }
```

A genuine tap (negligible movement on both axes, `TAP_MAX_MOVEMENT = 10`) falls through to `openCurrent()`. A real horizontal swipe returns early via the existing branches — unchanged, unaffected. A vertical scroll-drag (large `deltaY`) is neither a swipe (fails the direction-ratio check) nor a tap (fails the movement-threshold check), so it correctly does nothing — normal page scroll is never hijacked. This is why "a tap never fires mid-swipe and never fires on a scroll-drag": the three cases are mutually exclusive by construction, evaluated in the same handler against the same `deltaX`/`deltaY`, with no separate listener that could race or double-fire.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed a testing-methodology gap that produced false test failures during Task 3/4/5 verification (not a product bug)**
- **Found during:** Isolated e2e verification of Tasks 3-5, before committing
- **Issue:** Three related test-authoring bugs, not app bugs: (a) `page.mouse.move()` with a single direct jump (steps:1, the default) does not reliably synthesize `mouseenter`/`mouseleave` in headless Chromium — confirmed via a targeted debug script comparing single-jump vs. multi-step moves; (b) my initial "center"/"mid-height" test coordinates (photo bounding-box center) actually land on the `.home-hero__accent` panel (a sibling positioned on top, spanning roughly the right half + bottom half of the hero) or the fixed `SiteHeader` (top ~148px), both of which intercept hit-testing above the photo and were silently swallowing the mousemove/click; (c) reading `background-color` immediately after a move samples mid-transition (the CSS `background 200ms ease`), not the settled value.
- **Fix:** Added `{ steps: 10 }` to every hover-cursor/peek mouse.move call; moved test pointer coordinates to a region clear of both the header (`y > 148px`) and the accent panel (`x < 598px` or `y < 338px`) — settled on `box.height * 0.3` for the vertical test coordinate; switched the accent-color assertion from a one-shot `evaluate()` comparison to `toHaveCSS()`'s built-in polling.
- **Files modified:** `tests/e2e/homepage.spec.ts` only (no app code changed)
- **Verification:** All 17 new cursor/peek/click tests pass individually and together; confirmed via temporary debug scripts (deleted before commit) that isolated each root cause precisely.
- **Committed in:** `e24d5d2`, `98bcf66` (folded into the Task 4/5 commits that introduced the affected tests — no separate fix commit needed since the tests hadn't been committed with the bug yet)

**2. [Rule 1 - Bug] Un-gated `.home-hero__cursor`'s base invisible/out-of-flow CSS — found by the orchestrator's live-browser verification, not this executor's own e2e suite**
- **Found during:** Orchestrator's independent live Playwright MCP browser verification (mobile-emulated context, `hasTouch: true, isMobile: true`, 390x844), AFTER this executor's own commits and e2e run had already reported green.
- **Issue:** `.home-hero__cursor`'s entire CSS rule — including base/resting properties like `position: absolute`, `opacity: 0`, and `pointer-events: none` — lived only inside `@media (hover: hover) and (pointer: fine)`. On a touchscreen, where that media query never matches, the element received ZERO styling and fell back to browser defaults: `position: static`, `display: block`, `opacity: 1`, full container width (`390px`) — a real, laid-out, visible block reading "OUVRIR→" in dark ink at the top of the photo. This executor's own e2e suite never caught it: no test asserted the cursor's computed style on a touch-emulated context (only its markup existence and desktop-hover states were covered).
- **Fix:** Split the base properties that must hold on every device (`position: absolute; top: 0; left: 0; opacity: 0; pointer-events: none;`) into an ungated rule; everything else (sizing, colors, zone-morph states, transitions, the `is-cursor-active` opacity:1 activation, and `cursor: none` on `.home-hero__photo`) stays gated inside the media query exactly as before — those genuinely only belong on real-mouse desktop, and `is-cursor-active` is only ever added by the already-`hoverCapable`-gated script.
- **Files modified:** `src/components/HomeCarousel.astro` (CSS split), `tests/e2e/homepage.spec.ts` (new regression test)
- **Verification:** Confirmed the bug reproduces by temporarily reverting the fix locally and re-running the new regression test (it correctly failed: `opacity: '1'` instead of `'0'`); restored the fix and re-confirmed green. Re-ran the full e2e suite (227/227, including the new test) and full unit suite (154/154) after the fix. Directly measured `getComputedStyle` on a fresh `devices['iPhone 14 Pro']`-emulated page: `opacity: '0'`, `position: 'absolute'`, `pointerEvents: 'none'` — not relying on the header happening to visually mask the element, as the original screenshot-only check had.
- **Committed in:** `f59bf73` (separate, atomic follow-up commit, not amended into the Task 3 commit)
