<objective>
Make Sanity content publishes reach the real production domain automatically, while keeping every other production deploy behind the existing human-approval gate.

Today `.github/workflows/deploy-ovh.yml` has a single `workflow_dispatch` trigger and its deploy job is gated on the `production-ovh` GitHub Environment's Required reviewer. That was correct for the initial risky launch (D-01/D-02), but it means Romane — non-technical, no GitHub access — cannot get a new photo onto atelierjacquelinesuzanne.fr without Florian manually running and approving a workflow. `.github/workflows/deploy.yml` already auto-rebuilds GitHub Pages staging on `repository_dispatch` type `sanity-content-published` (fired by a Sanity publish webhook); production must now ride the same signal.

Purpose: Close the last manual step in the content-publishing loop so the artist can self-serve her own site, without weakening the deliberate-human-action gate on code deploys.

Output: deploy-ovh.yml triggered by both `workflow_dispatch` and the Sanity `repository_dispatch`, with a trigger-conditional approval gate; updated source-invariant unit tests; README "Deployments" documentation for the two production paths and the new one-time environment setup; and a dated supersession note under D-01 in 05-CONTEXT.md.

**Mechanism this plan depends on (verify before writing, do not assume):**

GitHub Actions allows an expression in `jobs.<job_id>.environment.name`, evaluated with the `github` context. This is the ONLY way to make an approval gate conditional — there is no `if:` that can disable a Required reviewer, and protection rules are a property of the environment, not of the job. So "approval for some triggers, not others" necessarily means TWO environments: the existing reviewer-protected `production-ovh`, and a new unprotected `production-ovh-auto`.

Consequence that must not be missed: GitHub **environment** secrets are scoped per environment. `OVH_SFTP_PASSWORD` was set with `gh secret set OVH_SFTP_PASSWORD --env production-ovh` (see README one-time setup step 1), so it is NOT visible to a job that resolves to `production-ovh-auto`. The secret must be duplicated onto the new environment (declared in this plan's `user_setup`), and the workflow must fail loudly when it is absent rather than handing an empty password to the SFTP action.

Existing trigger syntax to mirror verbatim from `.github/workflows/deploy.yml` lines 11-12:
`repository_dispatch:` with `    types: [sanity-content-published]`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Sanity webhook → GitHub `repository_dispatch` | An external HTTP caller holding a repo-scoped token can now start a production deploy that no human approves. |
| GitHub Environment → OVH SFTP | A second environment now holds a copy of the production SFTP credential. |
| `main` branch HEAD → production | The automatic path builds the default branch, so a content event ships whatever code is currently on `main`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-v3t-01 | Elevation of Privilege | `repository_dispatch` trigger on deploy-ovh.yml | medium | accept | Firing this event already requires a token with write access to the repo — an attacker holding that could push to `main` and reach production by other means anyway. The automatic path runs every blocking gate (typecheck, artifact verification, Playwright, Vitest coverage) before any upload, so it cannot ship a broken artifact. Residual risk accepted as the explicit cost of the D-01 supersession. |
| T-v3t-02 | Tampering | `main` HEAD shipped by a content-only event | high | mitigate | Cannot be eliminated without pinning the auto build to a last-deployed commit (out of scope for a quick task). Mitigated by documentation: the caveat is stated in the workflow header comment AND in a dedicated README paragraph — keep `main` production-ready, because a Sanity publish releases it. |
| T-v3t-03 | Information Disclosure | duplicated `OVH_SFTP_PASSWORD` on `production-ovh-auto` | medium | mitigate | Keep the credential environment-scoped (never promote it to a repo-level secret, which would expose it to every workflow and every branch). Both SFTP action references stay pinned to the immutable commit SHA, so third-party code with the secret in scope cannot change under a moved tag. |
| T-v3t-04 | Denial of Service | empty secret → unauthenticated SFTP attempts | low | mitigate | New `Guard: SFTP credentials are present` step fails the job with an explicit `::error::` before the first upload, converting a silent misconfiguration into a loud, actionable failure. |
</threat_model>
