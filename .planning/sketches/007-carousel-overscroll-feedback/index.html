Why these three

Research into "commit gesture" patterns (pull-to-refresh, the closest real-world analog) found that credible implementations always pair a deliberate threshold with progressive visual feedback as you push past it, and let you back out before the threshold with no trace left behind. Variant A adds a small dedicated element; B reuses existing chrome instead of adding anything new; C uses no chrome at all, just a physical response on the content itself. All three share the identical accumulator/threshold logic (150px, matching the shipped OPEN_OVERSCROLL_THRESHOLD) — only the visual response differs.

Note on the demo itself: this sketch calls preventDefault() on wheel and sets touch-action:none so the gesture stays contained inside the little frame instead of scrolling this sketch page. That is a sketch-only necessity — the real implementation must keep its listeners passive and never call preventDefault(), exactly as today (quick-260725-sj4/cfm), regardless of which variant is chosen.

Learned by building this: the shipped accumulator only resets lazily, on the next scroll event after the 800ms idle window. That's invisible today because there's no feedback to leave stale. Once there IS visible feedback, it needs a proactive decay — if you stop pushing, the indicator should visibly recede back to rest on its own (not just sit there until you scroll again) so "letting go" reads as cancellation, matching the pull-to-refresh research directly. This sketch's idle watchdog (decays after 800ms of no forward input) demonstrates that; the real implementation should adopt the same proactive decay, whichever variant is chosen.
