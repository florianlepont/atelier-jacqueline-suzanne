## Resolution

root_cause: "Not a code defect — the code faithfully implements plan 21-10's assumption A4 exactly as specified and recorded: two independent, ordinary-flow, full-viewport `<div>` sections (`.home-scroll-deck__intro`, `data-intro-beat=\"1\"`/`\"2\"`), each rendering its OWN separate `<img class=\"home-scroll-deck__intro-logo\">` at identical static CSS geometry (fixed 40vw/220px-cap width, centred via a 3-row CSS grid that decouples the logo's row from the secondary content's height). Continuity between beats is faked purely through matched styling, not through a shared element or any scroll-driven transform. The runtime driver confirms there is zero continuous scroll-scrub logic for the intro: `applyArrival()` only binary-toggles an `.is-revealed` class on the section (driving ONLY the tagline's D-13 opacity/translateY reveal, never touching the logo `<img>` at all) once a section crosses a 98% visibility threshold — the same discrete mechanism used for unrelated gallery-slide description reveals. Separately, `computeProgress()`/`applyIntroActive()` derive only a BOOLEAN `data-intro-active` flag (for header-hide), reading the ZOOM track's rect, not a continuous 0..1 progress value applied to the intro. So there is no code path anywhere that could make the logo appear to shrink or transform continuously — by construction, two separate static logo instances are shown in two separate static sections, exactly matching the reported symptom. A4's plan text explicitly named and rejected the single-pinned-section alternative on purpose, reasoning that a second pinned/scrubbed stage would reintroduce the handoff-desynchronisation risk class plan 21-07 had just fixed (`21-UAT.md` gap 2) — a real, deliberate engineering trade-off, not an accidental omission."
fix: "Not applicable (goal: find_root_cause_only). Fix DIRECTION for a future gap-closure plan, grounded in two existing, precedented in-codebase patterns for exactly this shape: (1) src/lib/home-carousel.ts's `computeZoomProgress(trackTop, revealDistance)` + `computeWordmarkZoomState(t)` pair, driving HomeCarousel.astro's single `.home-scroll-deck__wordmark` element continuously from a `position: sticky` stage inside a document-tall pinned track; (2) src/components/DetailHero.astro's `.detail-hero__pin` sticky panel, whose `onProgress(t)` lerps a SINGLE photo element's width via inline styles and reveals dependent content (title, format line) via `clamp01((t - offset)/span)` sub-ranges of that same `t`. The redesign replaces the two independent A4 sections with ONE pinned/scrubbed intro block containing exactly one logo `<img>` and the tagline as siblings, adds a new pure `computeIntroProgress()`-style function (mirroring `computeZoomProgress`, unit-testable the same way) reading the intro track's own live rect over a new `INTRO_REVEAL_DISTANCE`, and drives the logo's scale/position AND the tagline's opacity/translateY continuously from that SAME t inside the existing per-frame `frame()` loop (extending `applyProgress`/`onProgress`, not `applyArrival`) — removing the intro sections from the binary-threshold `arrivalTargets`/`applyArrival()` pass entirely, since a continuous scrub is a different mechanism than a visibility-threshold reveal.

  Structural implications this reopens (flagged per the investigation note, not resolved here):
  - Pre-zoom scroll-track geometry: A4's cost model was flat and exact — two static 100svh sections = a fixed 2-viewport-height pre-zoom distance, with zero interaction with `ZOOM_REVEAL_DISTANCE`/`computeZoomProgress` because those key off the (separate, downstream) zoom track's own rect regardless of what precedes it. A single pinned/scrubbed intro section changes this shape to `100vh (sticky stage) + INTRO_REVEAL_DISTANCE (scrub distance)` — analogous to the zoom track's own `calc(100dvh + var(--zoom-reveal-distance))`. The zoom's OWN math still needs zero change (same invariant, still holds, `computeZoomProgress` is unaffected by what's above the zoom track in the document) — but the total pre-zoom scroll distance is no longer fixed by construction; `INTRO_REVEAL_DISTANCE` becomes a new real-device pacing decision (mirroring how `ZOOM_REVEAL_DISTANCE`'s 900px 'Cinematic' pace was chosen from three tested candidates per D-02/D-04), and every e2e scroll-target helper built on `getIntroOffset()` (21-10 Task 3) would need re-deriving, not just re-running, since the offset itself would depend on new pacing constants, not a fixed 2-viewport-heights literal.
  - Tagline reveal timing: currently reuses D-13's opacity/translateY/180ms-ease values VERBATIM inside a discrete class-toggle (`is-revealed` at 98% visibility) — the same code path gallery slide descriptions use. A continuous scrub instead wants the tagline revealed via a sub-range of the SAME progress `t` driving the logo (matching DetailHero's `titleT = clamp01((t - 0.3) / 0.3)` idiom) — a materially different mechanism needing its own new sub-range constants tuned on a real device, not a reuse of the existing discrete D-13 values, and decoupled from `ARRIVAL_THRESHOLD`/`applyArrival()` (which should then apply only to the actual gallery slides again).
  - Interaction with the zoom's own scroll-track: A4's own recorded reasoning already flags the core risk here — chaining a second pinned/scrubbed stage immediately before the zoom's existing pinned/scrubbed stage reintroduces a second handoff boundary, the same class of defect plan 21-07 fixed for gap 2 (zoom-to-slide handoff). The redesign needs the identical rigor that fix used (progress AND arrival re-derived from live `getBoundingClientRect()` every painted frame, zero reliance on `scroll` events or `IntersectionObserver` callback timing) applied to this NEW intro-to-zoom boundary, plus real-device verification that a fast fling through the intro-to-zoom handoff doesn't produce the same overlapping-crop-style glitch gap 2 exhibited before its fix."
