## Eliminated

- hypothesis: "The CSS track-height custom property (`--zoom-reveal-distance`) and the JS `ZOOM_REVEAL_DISTANCE` constant desync, so the sticky release point and the crossfade-complete point (t=1) land at different scroll offsets."
  evidence: Both are derived from the exact same source at build time. `HomeCarousel.astro`'s frontmatter writes `style={\`--zoom-reveal-distance: ${ZOOM_REVEAL_DISTANCE}px\`}` (line 371) directly from the imported `ZOOM_REVEAL_DISTANCE` constant (`src/lib/home-carousel.ts:209`, value 900), and the client script imports and uses the literal same constant (`import { ZOOM_REVEAL_DISTANCE, ... } from '../lib/home-carousel'`, line 1654; used in `computeProgress()` at line 1791). There is no independently-hand-maintained second number anywhere (the WR-01 fix from 21-04 specifically eliminated that risk). Geometrically: track height = `100dvh + 900px`, stage height = `100dvh` (sticky), so the stage naturally releases exactly when scroll has advanced 900px past the track's top — the identical number `computeZoomProgress` divides by. `dvh`'s live changes (iOS Safari toolbar collapse) cancel out of this delta since both the track and the stage heights carry the same `dvh` term. This mechanism is real but not the cause: the two numbers cannot literally drift apart because they are the same literal value passed to two different consumers, and the geometry that determines the *release point* factors dvh out algebraically.

  checked: `src/components/HomeCarousel.astro` lines 3489-3494 (`.home-slide` — `scroll-snap-align: start; scroll-snap-stop: always;`) and lines 3636-3663 (`is:global` block — `html:has(.home-scroll-deck) { scroll-snap-type: y proximity; }`, disabled only under reduced motion)

The zoom track/stage deliberately carry no `scroll-snap-align` (Pitfall 6 in `21-RESEARCH.md` was specifically about avoiding this), so the 900px zoom scrub itself is correctly snap-free — but the FIRST snap point in the whole page is exactly at the start of `.home-slide` index 0, i.e. exactly the same scroll offset (`trackTop = -900px`, `t = 1`) where the crossfade/header-hide/arrival-reveal are all supposed to complete. `scroll-snap-stop: always` additionally forces the browser to hard-stop scroll momentum AT that boundary rather than letting a fast fling glide past it.
  implication: The exact scroll offset where three independent systems are all supposed to reach their "done" state simultaneously — (1) native CSS `position: sticky` release [continuous, paint-synchronous, always exactly correct], (2) the JS crossfade/`data-zoom-active` flag [event-driven, lags behind real scroll position whenever `scroll` dispatch is throttled/coalesced], and (3) the `IntersectionObserver` arrival reveal [async, browser-batched] — is also the exact scroll offset where the browser's own native scroll-snap machinery is most likely to perform an abrupt, compositor-driven position correction (a hard stop forced by `scroll-snap-stop: always`, arriving via `proximity` snap). A native snap adjustment of this kind is well documented (especially on iOS Safari) to move the composited scroll position in a way that does not dispatch a matching 1:1 stream of `scroll` events — WebKit is known to throttle/coalesce `scroll` event dispatch heavily during momentum/fling and snap-settling scrolling, decoupling the actually-rendered (GPU-composited) scroll offset from what JS scroll listeners have most recently observed.

## Resolution

root_cause: |
  Three independently-timed systems are all designed to reach their "done" state at the exact same scroll offset (`trackTop = -900px`, i.e. zoom progress t=1, which is also the page's first CSS scroll-snap point at the start of gallery slide 0):
    1. Native, purely-CSS `position: sticky` release of `.home-scroll-deck__stage` — always exactly synchronized with the true composited scroll position, because the browser computes it as part of layout/paint on every frame regardless of JS.
    2. The zoom driver's crossfade state (`wordmark`/`photoLayer` opacity+scale, and the `data-zoom-active` attribute that hides/shows the header) — written ONLY from `onProgress()`, which only runs inside a `scroll`-event-triggered, rAF-batched callback (`src/components/HomeCarousel.astro` lines 1794-1800, plan 21-05). There is no independent per-frame polling loop.
    3. The arrival `IntersectionObserver`'s `is-revealed` reveal (title/description/accent-panel), delivered via the browser's own asynchronous, batched `IntersectionObserver` callback timing (plan 21-06).

  `.home-slide` carries `scroll-snap-align: start; scroll-snap-stop: always;` and the whole page is a `scroll-snap-type: y proximity` container (`html:has(.home-scroll-deck)`), so exactly at this same scroll offset the browser also performs a hard, compositor-driven scroll-snap correction forcing the scroll position to settle at slide 0's start, even against a fast fling. On a real phone, `scroll` event dispatch is well known (especially on iOS Safari/WebKit) to be throttled/coalesced during momentum/fling scrolling and during native scroll-snap settling — so the ACTUAL, rendered/composited scroll position (and therefore the native sticky-release) can advance to/past t=1 one or more frames before the JS's `scroll`-driven `onProgress()`/`onArrival()` callbacks fire again with the corresponding update.

  During that window, the pinned stage — already unpinning/scrolling away because its geometry is governed purely by the (already-advanced) native scroll offset — is still rendering a STALE, mid-crossfade JS state (a partially-opaque, greatly up-scaled wordmark text-cutout of the photo, i.e. one "crop"/zoom-level of the gallery image) while the just-arrived first slide underneath (also purely native/composited, needing no JS) is simultaneously visible showing its own flat, unscaled cover-crop of the SAME image — a second, different-looking "crop" of the identical photo. Because `data-zoom-active` is also stuck at its stale `'true'` value and the arrival observer hasn't yet fired `is-revealed` for slide 0, the header, accent panel and title are all still absent during this same frame. Once the delayed `scroll` event/rAF tick (and the `IntersectionObserver` callback) finally fire — which the ~0.2s gap between the two sampled video frames is consistent with — `onProgress(1)`/`onArrival` run, flipping `data-zoom-active` to `'false'` (fading the header in) and toggling `is-revealed` (revealing title/description/accent), while by then the stage has already scrolled fully off-screen, producing the clean, correctly-settled first-slide view the user sees ~0.2s later.

  This is a newly-exposed instance of a latent assumption in the ported driver pattern (`DetailHero.astro`, desktop-only, no touch/momentum scrolling, no coincident `scroll-snap-stop` boundary) that `scroll` events fire densely/promptly enough to keep a JS-driven visual state in lockstep with the true native scroll position — an assumption that silently breaks specifically under real touch/momentum/scroll-snap physics on a real phone, which neither the Chromium nor the desktop-WebKit-emulated `webkit-mobile` Playwright project can reproduce (both explicitly flagged as insufficient for this exact class of check in `21-05-PLAN.md`/`21-06-PLAN.md`'s own verification sections).
