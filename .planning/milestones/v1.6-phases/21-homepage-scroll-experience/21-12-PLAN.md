<objective>
Close `21-UAT.md` round-2 gap 3 (`.planning/debug/homepage-scroll-cover-photo-doubled.md`): remove the full viewport-height of scrollable dead zone that currently sits between zoom completion and the first slide's snap point, during which the zoom's crossfade photo layer and the first slide's own photo are both on screen showing pixel-identical crops of the same source image.

Purpose: the zoom motion itself is confirmed clean — plan 21-07's per-frame loop fixed the transition-frame staleness. What no plan addressed is that the crossfade layer's CONTAINING BOX keeps occupying a full viewport height of layout after its opacity animation finishes. The pinned stage releases exactly where progress reaches 1, but at that instant the track's bottom edge — where the first slide begins — is still a whole viewport height below the fold. Scrolling through that ~852px zone shows the stage's `cover, center` crop of `firstGallery.heroSrc` finishing its exit while the slide's own `object-fit: cover` crop of the same image restarts from its top edge directly beneath it: a hard seam where the same photograph appears twice. `scroll-snap-type: y proximity` only engages within roughly 250-400px of a snap point (measured live in the debug session), far short of covering the zone, so a real gesture very plausibly rests inside it.

The fix is the one `21-UAT.md`'s `missing` list names first: make the first slide's snap point coincide with the stage's release point, so the dead zone has zero length. Every geometry change is keyed on `data-zoom-active`, the attribute only the motion driver ever writes — which is what keeps reduced-motion, desktop and pre-JS rendering byte-for-byte unchanged.

Output: four CSS rules in `src/components/HomeCarousel.astro`, and rebased plus new cases in `tests/e2e/homepage-scroll-deck.spec.ts`.
</objective>

<geometry_note>
## The arithmetic this plan changes, stated once

Let `V` be the deck viewport height (`var(--deck-vh, 100svh)`, plan 21-11) and `D` the zoom reveal distance.

**Today:** track height is `V + D`; the sticky stage (height `V`, `top: 0`) releases when the track's bottom reaches the stage's bottom, i.e. at `trackTop = -D` — exactly where `computeZoomProgress` reaches 1. At that scroll position the track's bottom edge, and therefore the first slide's top edge, sits at `+V`: the very bottom of the screen. A further `V` of scrolling is needed before the first slide fills the viewport. That `V` is the dead zone.

**After this plan:** the slides wrapper is pulled up by exactly `V` while the driver is attached. The track's own height, the stage's own height, the sticky release point and every zoom-progress number are all unchanged — this plan touches none of that math. What changes is only where the slides sit relative to the track: the first slide's document offset becomes `trackOffset + D` instead of `trackOffset + V + D`. So at the instant progress reaches 1, the first slide's top is at 0 and its own `scroll-snap-align: start` point coincides with the stage's release point. The dead zone is zero.

**The consequence that must be handled:** because the slides moved up, the first slide is now geometrically behind the stage for almost the whole scrub — it enters the viewport's bottom edge once the scrub has covered `V - D` px, which for the shipped 900px/852px values is only about 48px in. The stage must therefore be opaque and stacked above the slides for the duration, and must go out of sight the instant progress completes. Those are the second and third CSS rules below, and they are not optional decorations — without them the fix is worse than the bug.

**A deliberate, accepted side effect:** the first slide's snap point now sits `D` px after the track's top instead of `V + D`, which puts it within `proximity` snap range of the tail of the scrub. A resting scroll position in the last ~250-400px of the zoom can therefore be pulled forward to completion. This is desirable, not a regression: it removes the ability to come to rest mid-zoom in a half-scaled state, and it firms up arrival at the first slide without touching `scroll-snap-type` (21-RESEARCH.md Pitfall 6 stays intact — the snap mode is unchanged, only the distance to the nearest snap point changed). Record it in the CSS comment as an accepted consequence, and see Task 2 item 3 for what it means for existing mid-scrub e2e targets.
