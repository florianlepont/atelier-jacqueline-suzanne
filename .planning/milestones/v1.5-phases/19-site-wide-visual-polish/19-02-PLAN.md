<objective>
Restore the halftone dot-texture's bleed to the true browser viewport edges on Contact, About and Éditions (UI-01, per D-03), without reintroducing the horizontal-overflow bug or the `position: sticky` breakage that this exact class of change already caused once in production (D-04). The regression net demanded by D-05 is written FIRST, so the guards are green on the pre-change tree before the risky CSS is touched.

Purpose: the current `overflow-x: clip` containment fixed the overflow bug by hard-cutting the texture at the content column's edge — which is the visual defect UI-01 reports. This plan replaces containment-by-clipping with containment-by-geometry: the halftone's own box is made exactly client-width, so it cannot overflow the document in the first place.
Output: one new e2e regression spec, one component style edit, and a reconciled visual baseline.
</objective>

<planning_measurements>
These four findings come from isolated browser measurements taken at planning time (headless Chromium 1228 + WebKit 2311, viewports 1280 and 1920, on a reduced replica of the real DOM: centered `min(100%, 1180px)` container + `padding-inline: clamp(16px, 4vw, 48px)` + `position: relative` header + absolutely-positioned halftone). Two of them contradict PATTERNS.md's recommendation — trust these, and do not re-litigate them from first principles:

1. **Keeping `overflow-x: clip` on `.page-title-header` DEFEATS any child full-bleed.** With the clip in place and the halftone at `left/right: calc(50% - 50vw)`, the halftone's box measured the full viewport width (rect 0 -> 1280) but painted NOTHING outside the header box — pixel output in the leftmost 30px strip was byte-identical to the clipped baseline. PATTERNS.md's suggestion to keep the clip "as a safety net" is not viable: the clip and the bleed are mutually exclusive. The clip must be removed, and the safety must come from the halftone's geometry instead.
2. **`overflow-clip-margin` is a dead end.** With mixed axes (`overflow-x: clip` + `overflow-y: visible`) Chromium ignores it entirely. With both axes clipped it works visually but DOES contribute the clip-margin region to the document's scrollable overflow — measured +602px of horizontal overflow at 1280 and +282px at 1920, i.e. it recreates exactly the bug being avoided. WebKit appears not to honour the property at all, so it would also be Chromium-only.
3. **`left/right: calc(50% - 50vw)` on the halftone is geometrically correct and overflow-free.** Measured rect exactly `0 -> clientWidth` with `documentElement.scrollWidth === clientWidth` (zero horizontal overflow) in BOTH Chromium and WebKit, at 1280 and 1920. This is the technique to use. Note `50%` here resolves against the halftone's containing block (`.page-title-header`), which is why `.page-title-header` must keep `position: relative`.
4. **The mask focal point MUST be re-anchored, or the texture will stop short of the right edge.** The mask is `radial-gradient(circle 640px at right 700px top 700px, ...)`, i.e. the focal point sits 700px in from the halftone's own right edge — which today lands exactly on the header box's top-right corner (because the box is `right: -700px`). Once the box's right edge becomes the viewport's right edge, that same `right 700px` moves the cloud ~600px left: measured result was ink reaching the LEFT viewport edge and NO ink in the rightmost 30px strip — the opposite of what UI-01 asks for. The fix is to express the focal point as the real distance from the viewport's right edge to the header's right edge.

**Focal-point formula** (derived, then arithmetic-checked): distance = `50vw - min(100vw, var(--editorial-page-max)) / 2 + var(--editorial-page-padding-inline)`. Check at 1280px: 640 - 590 + 48 = 98px, and the header box's right edge is indeed at x=1182 (98px from the edge). Check at 1920px: 960 - 590 + 48 = 418px, header right edge at x=1502. Valid for all three consumers because `.contact-page` (ContactPageBody.astro line 114-117), `.about-page` (AboutPageBody.astro line 205-208) and `.editions-list` (EditionsOverviewBody.astro line 69-72) all use `width: min(100%, var(--editorial-page-max))` + `padding-inline: var(--editorial-page-padding-inline)`.

**Known residual, must be documented in code, cannot be caught by CI:** viewport units are scrollbar-inclusive. On a platform that draws space-taking scrollbars (Windows/Linux Chrome, or macOS with "Show scroll bars: Always"), `50vw` includes half the scrollbar, so the halftone's right edge can land up to ~half a scrollbar width (7-8px) past the client edge and produce a small horizontal scrollbar. The headless browsers CI runs use overlay scrollbars (measured `innerWidth - clientWidth === 0` even with classic-scrollbar flags forced), so no automated test in this repo can observe it. Record it in the component comment, check for it during the end-of-phase human verification, and only if a real horizontal scrollbar appears there, add a guard term to the RIGHT inset (`right: calc(50% - 50vw + 8px)`) and note the resulting narrow dot-free strip at the right edge in the summary.

**Scope clarification for roadmap success criterion 2:** the halftone is `display: none` below 760px (PageTitleHeader.astro line 178 + the `min-width: 760px` block at 183-187). "Bleeds to the true edges at mobile widths" is therefore not achievable by design — there is no texture below 760px. Do NOT enable it there; instead assert the `display: none` behavior is preserved.
